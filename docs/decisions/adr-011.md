# ADR-011 — Spring types in service code

**Status:** Accepted (2026-11-19, owner decisions ND3 and ND15). Refines [ADR-009](adr-009.md) and
[ADR-003](adr-003.md).

**Decision:** a service written on the platform imports Spring types, not platform types. The platform is
auto-configuration: it supplies property defaults, customizers and beans of Spring types, and steps back
when the service defines its own. Each capability is one Auto Configuration module and one POM-only
Starter. An API or SPI module exists only where no Spring type fits, and only with a recorded decision.

**Why:** a platform API is a second framework to learn, document and keep compatible, on top of Spring.
Spring Boot 4 already has a type for almost every extension point the platform wrapped (`RestClient.Builder`,
`RabbitTemplate`, `ProblemDetail`, `ApplicationEventPublisher`, ...). With one provider per capability,
an SPI has nothing to choose between.

**Consequence:** the platform's API modules are removed capability by capability
([Spring-native plan](../spring-native/plan.md)), and every guarantee they carried moves into
auto-configuration with a test. A guarantee that needs a platform type keeps one, named in an ND decision.

See also: [Spring-native decisions](../spring-native/decisions.md).
