# Lab: data

You give a generated service an entity, a repository and a migration, run it on H2, then run the same project on
Oracle Free and stop the database under it. You watch auditing fill in a column, a duplicate become a 409 that names
no table, a log line refuse to load an entity, and the database's outage stay out of readiness. About fifteen
minutes, most of it Oracle's first start.

**You need:** JDK 25, Maven 3.9, `curl`, Docker with about 3 GB of free memory, this repository, and
`PLATFORM_HOME` set to it ([labs](../index.md)). **Capability:** [data](../../modules/data.md); background in
[chapter 8](../../book/chapters/08-data.md).

## Step 0 — Put the platform in a local Maven repository

Nothing is published yet. This builds your checkout into a repository of its own, `~/.m2-hardening/lab-data`, with no
older platform artifact in it:

```bash lab-step
PLATFORM_REPO=$(bash "$PLATFORM_HOME/tooling/hardening/native-repo.sh" lab-data)
export PLATFORM_REPO
echo "platform repository: $PLATFORM_REPO"
```

## Step 1 — Generate the service

```bash lab-step
mvn -B -q -o -Dmaven.repo.local="$PLATFORM_REPO" \
    org.apache.maven.plugins:maven-archetype-plugin:3.1.2:generate -DarchetypeCatalog=local \
    -DarchetypeGroupId=ae.gov.dubaicustoms.platform -DarchetypeArtifactId=platform-service-archetype \
    -DarchetypeVersion=1.0.0-SNAPSHOT -DgroupId=com.example -DartifactId=depot \
    -Dpackage=com.example.depot -Dfeatures=data -Ddatabase=oracle -DinteractiveMode=false
cd depot
```

`-Ddatabase=oracle` puts the Oracle starter in the `pom.xml`: the driver, Flyway and Flyway's Oracle module. H2 still
backs runs without a datasource, which is where you start.

## Step 2 — An entity, a repository, a migration

A shipment has a unique reference, and auditing records who created it and when. Only JPA and Spring Data types:

```java lab-file src/main/java/com/example/depot/Shipment.java
package com.example.depot;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EntityListeners;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import java.time.Instant;
import org.springframework.data.annotation.CreatedBy;
import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;

@Entity
@EntityListeners(AuditingEntityListener.class)
public class Shipment {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String reference;

    @CreatedBy
    private String createdBy;

    @CreatedDate
    private Instant createdAt;

    protected Shipment() {
    }

    public Shipment(String reference) {
        this.reference = reference;
    }

    public Long getId() {
        return id;
    }

    public String getReference() {
        return reference;
    }

    public String getCreatedBy() {
        return createdBy;
    }
}
```

```java lab-file src/main/java/com/example/depot/ShipmentRepository.java
package com.example.depot;

import org.springframework.data.jpa.repository.JpaRepository;

public interface ShipmentRepository extends JpaRepository<Shipment, Long> {
}
```

The table, written once for both databases (`numeric(19)` is `NUMBER(19)` on Oracle, which has no `BIGINT`):

```sql lab-file src/main/resources/db/migration/V2__create_shipment.sql
create table shipment (
    id         numeric(19) generated by default as identity primary key,
    reference  varchar(64) not null,
    created_by varchar(255),
    created_at timestamp with time zone,
    constraint uq_shipment_reference unique (reference)
);
```

And a controller. It logs the saved entity as a key-value pair, next to its identifier:

```java lab-file src/main/java/com/example/depot/ShipmentController.java
package com.example.depot;

import java.util.Map;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
class ShipmentController {

    private static final Logger log = LoggerFactory.getLogger(ShipmentController.class);

    private final ShipmentRepository shipments;

    ShipmentController(ShipmentRepository shipments) {
        this.shipments = shipments;
    }

    @PostMapping("/shipments")
    Map<String, Object> create(@RequestParam String reference) {
        Shipment saved = shipments.saveAndFlush(new Shipment(reference));
        log.atInfo().setMessage("shipment saved").addKeyValue("shipmentId", saved.getId())
                .addKeyValue("shipment", saved).log();
        return Map.of("id", saved.getId(), "createdBy", saved.getCreatedBy());
    }

    @GetMapping("/shipments/count")
    Map<String, Object> count() {
        return Map.of("count", shipments.count());
    }
}
```

## Step 3 — Run it on H2

```bash lab-step
mvn -B -q -o -Dmaven.repo.local="$PLATFORM_REPO" package -DskipTests
java -jar target/depot-*.jar --server.port=18090 --management.server.port=18091 > h2.log 2>&1 &
echo $! > ../app.pid
for attempt in $(seq 1 90); do
  curl -fs http://localhost:18091/actuator/health/readiness > /dev/null && break
  sleep 1
done
curl -s -X POST "http://localhost:18090/shipments?reference=SHP-1"; echo
```

Flyway applied both migrations at startup, and auditing recorded `"system"`: the platform's auditor, until you
declare your own:

```bash lab-check
grep -q 'Successfully applied 2 migrations' h2.log
curl -s -X POST "http://localhost:18090/shipments?reference=SHP-2" | grep -q '"createdBy":"system"'
```

## Step 4 — A duplicate, and an entity in a log line

```bash lab-step
curl -s -X POST "http://localhost:18090/shipments?reference=SHP-1"; echo
grep '"message":"shipment saved"' h2.log | head -1
```

The duplicate is a 409 problem with a stable code and a fixed detail. Nothing in it names the table or the constraint:

```bash lab-check
curl -s -X POST "http://localhost:18090/shipments?reference=SHP-1" > dup.json
grep -q '"code":"DC-DATA-0409"' dup.json
test "$(grep -ci 'uq_shipment\|shipment_reference\|insert' dup.json)" -eq 0
```

The log line has the identifier you logged, and `[entity Shipment]` where you logged the entity: the platform never
reads an entity, because reading one can run a query:

```bash lab-check
grep '"message":"shipment saved"' h2.log | grep -q '"shipment":"\[entity Shipment\]"'
grep '"message":"shipment saved"' h2.log | grep -Eq '"shipmentId":[0-9]+'
```

## Step 5 — The same project on Oracle Free

Start Oracle Free in Docker. Its first start copies its datafiles, which takes a few minutes. `APP_USER` creates a
user that owns its schema (for a production split between schema owner and runtime user, see the
[data page](../../modules/data.md)):

```bash lab-step
kill "$(cat ../app.pid)"
docker run -d --name "$LAB_RUN-oracle" --label "dc-lab=$LAB_RUN" -p 127.0.0.1::1521 \
    -e ORACLE_PASSWORD=lab-only-system -e APP_USER=DEPOT -e APP_USER_PASSWORD=lab-only-depot \
    gvenzl/oracle-free:23-slim-faststart > /dev/null
for attempt in $(seq 1 240); do
  docker logs "$LAB_RUN-oracle" 2>&1 | grep -q 'DATABASE IS READY TO USE' && break
  sleep 5
done
ORACLE_PORT=$(docker port "$LAB_RUN-oracle" 1521/tcp | head -1 | sed 's/.*://')
echo "Oracle on port $ORACLE_PORT"
```

Start the same jar against it. Production runs 19c and this container is 23ai, so pin Hibernate to 19:

```bash lab-step
java -jar target/depot-*.jar --server.port=18090 --management.server.port=18091 \
    "--spring.datasource.url=jdbc:oracle:thin:@//localhost:$ORACLE_PORT/FREEPDB1" \
    --spring.datasource.username=DEPOT --spring.datasource.password=lab-only-depot \
    --spring.jpa.properties.jakarta.persistence.database-major-version=19 > oracle.log 2>&1 &
echo $! > ../app.pid
for attempt in $(seq 1 120); do
  curl -fs http://localhost:18091/actuator/health/readiness > /dev/null && break
  sleep 1
done
curl -s -X POST "http://localhost:18090/shipments?reference=SHP-1"; echo
```

The same migrations ran on Oracle, and the same duplicate is the same 409:

```bash lab-check
grep -q 'Successfully applied 2 migrations' oracle.log
curl -s -X POST "http://localhost:18090/shipments?reference=SHP-1" | grep -q '"code":"DC-DATA-0409"'
```

## Step 6 — Stop the database

```bash lab-step
docker stop "$LAB_RUN-oracle" > /dev/null
START=$(date +%s)
curl -s http://localhost:18090/shipments/count > down.json
echo "answered after $(( $(date +%s) - START )) s"; cat down.json; echo
```

A request that needs the database gets a retryable 503 within the 5 s connection wait, instead of hanging:

```bash lab-check
grep -q '"code":"DC-DATA-0503"' down.json
grep -q '"retryable":true' down.json
test $(( $(date +%s) - START )) -le 30
```

Readiness stays UP, because one database outage must not take every replica out of rotation. The `dependencies` group
is where it shows:

```bash lab-check
curl -fs http://localhost:18091/actuator/health/readiness | grep -q '"status":"UP"'
test "$(curl -s -o /dev/null -w '%{http_code}' http://localhost:18091/actuator/health/dependencies)" = 503
```

## Step 7 — Bring it back

```bash lab-step
docker start "$LAB_RUN-oracle" > /dev/null
for attempt in $(seq 1 180); do
  curl -fs http://localhost:18091/actuator/health/dependencies > /dev/null && break
  sleep 2
done
curl -s http://localhost:18090/shipments/count; echo
```

The pool reconnects on its own. No restart:

```bash lab-check
curl -fs http://localhost:18091/actuator/health/dependencies | grep -q '"status":"UP"'
curl -s http://localhost:18090/shipments/count | grep -q '"count":1'
```

## Step 8 — Clean up

```bash lab-step
APP_PID=$(cat ../app.pid)
kill "$APP_PID"
for attempt in $(seq 1 30); do
  kill -0 "$APP_PID" 2>/dev/null || break
  sleep 1
done
docker rm -f "$LAB_RUN-oracle" > /dev/null
```

```bash lab-check
test "$(kill -0 "$APP_PID" 2>/dev/null && echo running)" != running
test -z "$(docker ps -aq --filter "label=dc-lab=$LAB_RUN")"
rm ../app.pid
```
