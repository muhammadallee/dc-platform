The registrar’s **static factory and deferred dependencies fix HI-0084’s registration-time initialization**. A handler merely depending on infrastructure also needed by the transport does not itself create a cycle: those dependencies finish before its post-processing. A reverse dependency can create one, however—see below.

`@ConditionalOnSingleCandidate(EventTransport.class)` remains valid on a static method; it checks bean definitions, not successful construction. Missing transport lookup through `ObjectProvider.getObject()` still produces a typed `NoSuchBeanDefinitionException`: `getBeanType()` resolves to `EventTransport`, so the analyzer’s check remains valid for startup failures. Missing `RabbitTemplate`, serializer or registry dependencies correctly do **not** match that check. With no transport definition, the condition normally omits the registrar altogether. [Condition semantics](https://docs.spring.io/spring-boot/api/java/org/springframework/boot/autoconfigure/condition/ConditionalOnSingleCandidate.html), [provider resolution](https://raw.githubusercontent.com/spring-projects/spring-framework/v7.0.1/spring-beans/src/main/java/org/springframework/beans/factory/support/DefaultListableBeanFactory.java).

Delivery before readiness was already possible because `subscribe()` starts the container immediately. **What changes is collaborator resolution on the delivery thread**: serializer/properties/registry creation can now block or fail there. Such failures enter delivery error handling, not Boot’s startup failure analyzer; a registry failure after successful invocation can even trigger a handler retry.
