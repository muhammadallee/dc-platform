# DC Platform — Capability & Feature Catalog

Internal Spring Boot chassis (`ae.gov.dubaicustoms.platform`), delivered as a **Hybrid Starter + SPI**
platform: ~24 capabilities, each sliced into `api` / `spi` / `impl` / `autoconfigure` / `starter`
modules, shipped on a single release train behind one BOM.

---

## 1. Common / Shared Features

Features that apply across every capability — the chassis "constitution".

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| **Starter-per-capability packaging** | Each capability is consumed by adding exactly one `platform-starter-<cap>` POM-only artifact; starters contain no code and aggregate `autoconfigure` + the named provider impl + its driver. | Mirrors `spring-boot-starter-*` so there is no new mental model; makes "what do I add?" a one-line answer. | Teams hand-assemble 5–8 artifacts per capability, drift in what they include, and hit `NoClassDefFoundError` at runtime instead of dependency-resolution time. |
| **Auto-configuration only (no God framework)** | Everything activates through `@AutoConfiguration` + `AutoConfiguration.imports`; there is no custom lifecycle, registry, container, or DI mechanism. No `@ComponentScan` of platform packages. | Standard Boot mechanisms mean standard debugging (`--debug` condition report, `@ImportAutoConfiguration`, `exclude=`), and Boot upgrades stay cheap. | A proprietary runtime becomes a second framework to learn, invisible to Boot's diagnostics, and every Boot upgrade becomes a platform migration project. |
| **Universal `@ConditionalOnMissingBean` back-off** | Every platform bean stands down the moment the application defines its own bean of that type/name. | "A set of defaults, not a cage" — override by declaration, never by forking or patching the platform. | Teams fork platform modules or resort to `BeanDefinitionOverride` hacks; the platform becomes a blocker rather than an accelerator. |
| **Per-capability kill switch** | `dc.platform.<cap>.enabled` (`matchIfMissing = true`) disables an entire capability wholesale; sub-features have their own switches (e.g. `…errors.map-validation`). | Gives operations a config-only escape hatch during an incident, and lets a service opt out without dependency surgery. | An incident caused by a platform default can only be fixed by a code change, rebuild, and redeploy. |
| **Immutable, prefixed, metadata-backed properties** | All config lives under `dc.platform.<cap>`, bound to immutable `record` `@ConfigurationProperties` with constructor binding, defaults in code **and** in `spring-configuration-metadata.json`. | IDE autocompletion and inline docs for every key; no mutable global config state; a single naming namespace that cannot collide with app config. | Config keys become undiscoverable folklore, defaults are duplicated inconsistently, and mutable properties beans invite runtime mutation bugs. |
| **Property deprecation contract** | Renaming a key requires a deprecation window declared in `additional-spring-configuration-metadata.json`; the `upgrade-check` goal scans a service's YAML for keys deprecated in the target version. | Property keys are a public API surface; silent renames break production configs that compile fine. | Upgrades silently drop configuration — a security or timeout setting stops applying with no error, and the failure surfaces in production. |
| **Lowest-precedence defaults via `EnvironmentPostProcessor`** | Platform opinions on *third-party* keys (`logging.config`, `management.*`, `spring.jpa.*`, `resilience4j.*`) are injected as named, lowest-precedence property sources (`platform-logging-defaults`, `platform-observability-defaults`, `platform-data-jpa-defaults`), visible in `/actuator/env`. | User configuration always wins, and `/actuator/env` shows exactly which source won — opinion without hijacking. | Either the platform hard-codes values users cannot override, or it ships no opinion at all and every service re-derives the same tuning. |
| **Three-audience package model** | `…<cap>` = consumer API, `…<cap>.spi` = extender contracts, `…<cap>.internal` = no guarantees (excluded from javadoc, japicmp, and banned by ArchUnit from application imports). | Three distinct compatibility promises let internals evolve freely while APIs stay stable. | Applications couple to internals, and any refactor becomes a breaking change — the classic "everything is public API" trap. |
| **Executable dependency constitution** | Allowed/forbidden edges (api↛impl, impl↛impl, starter↛starter, no cross-capability `.internal`, zero cycles), max depth 4, and per-category fan-out ceilings enforced by a custom `PlatformLayerRule` maven-enforcer rule + `banCircularDependencies`. | Architecture that is only documented decays; a merge-blocking gate that names the violated edge and the fix keeps it true. | Layering erodes within months: APIs pull in providers, starters chain, cycles appear, and the module graph becomes unrefactorable. |
| **ArchUnit `PlatformArchRules` in every module** | A shared rule-jar runs as `ArchConstitutionTest` in each module's test phase, catching package-level violations the POM graph cannot see. | Some violations (importing another capability's `.internal`) are invisible to Maven; ArchUnit closes that gap. | Package-level leakage passes the build even while the dependency rules "pass", giving a false sense of enforcement. |
| **Binary-compatibility gate (japicmp)** | japicmp diffs `-api` / `-spi` packages against the last release; `.internal` is excluded. | Makes SemVer a checked promise rather than an intention, which is what lets consumers upgrade the BOM confidently. | Accidental signature changes ship as patch releases and break every consumer at runtime with `NoSuchMethodError`. |
| **Single release train + one BOM** | All modules share one version; consumers import `platform-bom` and upgrade with one property change. `dependency-convergence` enforces one version per third-party across the reactor. | Eliminates the N×M version-compatibility matrix that kills feature-modular platforms. | Consumers must reason about which messaging version works with which security version; support cost explodes and upgrades stall. |
| **API stability markers** | apiguardian `@API(status, since)` on every public API/SPI type (STABLE / EXPERIMENTAL / DEPRECATED / INTERNAL), plus `@PlatformApi` / `@PlatformInternal`; enforced by ArchUnit (DEPRECATED must co-occur with `@Deprecated`). | Stability is readable straight from the jar at code time, before anyone opens documentation. | Developers cannot tell an experimental type from a load-bearing one and build production code on surfaces about to change. |
| **`CapabilityDescriptor` self-reporting** | Each capability contributes a descriptor (`name`, status, provider); rendered as a one-line startup banner and served at `/actuator/platform` as JSON. | Answers "what platform behaviour is actually live in this running instance, with which provider?" without reading POMs. | Diagnosing "why isn't X happening?" requires classpath archaeology; incident response slows measurably. |
| **`FailureAnalyzer`-based misconfiguration diagnostics** | Top misconfigurations produce Boot *Description / Action* blocks naming the exact fix: missing Flyway (data), no `EventTransport` (messaging), no JWT issuer (security), unwritable storage root. | A startup failure becomes a teaching moment instead of a stack trace hunt. | Every team independently rediscovers the same five misconfigurations through trial and error and support tickets. |
| **Ordered `*Customizer` extension tier** | Customizer beans (`ProblemDetailCustomizer`, `SecurityCustomizer`, `PlatformRestClientCustomizer`, `MeterRegistryCustomizer`, `OpenApiCustomizer`, `LogSanitizer`) are collected via `ObjectProvider…orderedStream()` and applied in `@Order`. | Lets a service *add* behaviour to a default without *replacing* the bean — the common case, at low cost. | Any small tweak forces wholesale replacement of a platform bean, and the service inherits maintenance of everything else that bean did. |
| **SPI provider tier + TCK certification** | Multi-provider capabilities publish an SPI and an abstract TCK test-jar (`EventTransportTck`, `ObjectStoreTck`, `LockProviderTck`, `FlagProviderTck`, `RateLimiterProviderTck`, plus audit and idempotency TCKs). A provider is certified iff the TCK passes — the same suite the platform's own providers pass. | Turns "implement this interface" into a verifiable contract, so third-party providers behave identically under swap. | Provider swaps become semantic minefields: subtly different TTL, ordering, or exclusion behaviour surfaces only in production. |
| **Classpath-driven provider selection** | Providers are selected by what's present (Redis over JDBC for locking/idempotency/ratelimit; S3 over filesystem for storage; OpenFeature over in-memory for flags; Redis over Caffeine for cache), never by a property. | One artifact change flips environments; no risk of a property naming a provider that isn't on the classpath. | Property/classpath mismatch fails at runtime, and dev/prod skew hides behind a config value nobody diffs. |
| **Correlation ID as a first-class thread** | One `CorrelationId` (32 hex) is read/generated at the servlet edge, published to MDC, echoed on the response, propagated to outbound REST calls (`X-Correlation-Id`), messaging headers, tracing baggage, problem bodies, and audit events. | Single-token traceability across logs, errors, messages, and downstream services — deliberately kept **out of metric tags** to avoid cardinality explosion. | Cross-service debugging degrades to timestamp correlation; a single request's path through the estate cannot be reconstructed. |
| **Docker-free-by-default test policy** | No test may require Docker, network, or credentials unless tagged `@Tag("docker")` and guarded by `assumeTrue(DockerAvailable.check())`; real infra runs only under `-Pdocker`. | Fast, hermetic builds on laptops and CI agents without a Docker daemon; contributors are never blocked by infrastructure. | Build times balloon, CI flakes on container pulls, and developers skip running tests locally. |
| **Five-case ContextRunner matrix per autoconfigure module** | Every autoconfigure module ships the same activation matrix: activates, backs off on user bean, backs off on kill switch, backs off on missing class, honours properties. | Auto-configuration bugs are conditional-logic bugs; a uniform matrix catches them consistently across 24 capabilities. | Silent activation/back-off regressions ship — the worst class of platform bug, because the symptom appears in the consumer, not the platform. |
| **Generated documentation & discovery surfaces** | `properties.md`, `error-codes.md`, `bom.md`, `platform-index.json`, `llms.txt`/`llms-full.txt`, the MCP server, and the Claude Skill are all generated at build time from authoritative sources (config metadata, error-code registry, BOM); freshness tests fail the build on drift. Tagged usage snippets in docs are compile-checked against the live API. | Hand-written mirrors rot; generation plus a drift gate keeps documentation provably true. | Docs diverge from code, teams follow stale examples, and trust in the documentation collapses. |
| **Machine-readable discovery for agents** | `platform-mcp-server --stdio` exposes six read-only tools (`find_capability`, `property_lookup`, `error_code_lookup`, `usage_example`, `list_starters`, `platform_version`) over the build-time index; the archetype emits `CLAUDE.md`, `AGENTS.md`, `.mcp.json`, `catalog-info.yaml`. | Coding agents are now a primary consumer of the platform; grounding them on an authoritative index prevents invented APIs. | Agents generate plausible-but-wrong vanilla-Spring code, and the platform's conventions are bypassed at the point of highest leverage. |
| **Consumer conformance rules (`PlatformUsageRules`)** | ArchUnit rules a *service* runs over its own code: no direct `KafkaTemplate`/`RabbitTemplate`, no hand-rolled `ResponseEntityExceptionHandler`, no `System.getenv`. Each failure names the platform alternative. | Enforcement at the consumer, where the mistake is actually made, and each failure teaches rather than merely blocks. | Services quietly bypass the chassis, and the cross-cutting guarantees the platform exists to provide stop holding fleet-wide. |
| **Dependency bans in `platform-service-parent`** | Declaring a wrapped library directly (spring-kafka, spring-rabbit, awssdk:s3, resilience4j, springdoc) fails the service build with a message naming the starter to use. | Catches bypass at dependency-declaration time — the earliest and cheapest possible moment. | The bypass is only discovered in code review, or never, and the wrapped library's version drifts out of BOM control. |
| **Migration automation (OpenRewrite)** | `platform-migrations` ships `AdoptPlatform` (swaps banned deps for starters, flags hand-rolled advice) and per-train `UpgradeTo_X_Y` recipes driven by deprecation metadata. | Makes adoption and upgrade a runnable command rather than a manual per-service project. | Adoption stalls at the effort barrier; older trains linger in production and the fleet fragments. |
| **`upgrade-check` Maven goal** | Resolves a target BOM, diffs managed versions against the project's current ones, scans `application*.{yml,properties}` for keys deprecated in that version, and emits `target/platform-upgrade-report.md`. | Turns "what breaks if we upgrade?" into a read-only, pre-commit answer. | Upgrades are attempted blind, fail mid-way, and get rolled back — reinforcing upgrade avoidance. |
| **Module scaffolding (`platform-build-maven-plugin:new-module`)** | Generates a compliant module skeleton (category, packages, POM wiring) so the boilerplate is never typed by hand. | Module sprawl is the known failure mode of this architecture; scaffolding removes the cost that causes shortcuts. | Contributors hand-copy modules, inherit stale config, and violate the constitution on the first commit. |
| **Service archetype + golden-path CI check** | A `maven-archetype` generates a ready-to-run service (parent, conformance test, slice tests, profile-aware `application.yml`, optional messaging/data/restclient samples with their tests); `golden-path.sh` (CI `generator-gate`) installs into an isolated repository → generates all 8 feature combinations outside the checkout → verifies → boots each jar → probes readiness, auth, the capability report and JSON logs, failing past a 10-minute per-service SLA. | Makes the developer experience an executable, continuously verified contract rather than an aspiration. | The onboarding path silently breaks between releases and is discovered by the next new team, at the worst possible moment. |
| **Platform test kit (`platform-starter-test`)** | One test-scoped starter bringing composed slices (`@PlatformTest`, `@PlatformMessagingTest`, `@PlatformDataTest`, `@PlatformWebTest`), fixtures (`TestTokens`, `assertThatProblem(...)`, `assertThatEvents(...)`), and guarded singleton `Containers`. | Services test the same way the platform is built; test setup stops being per-service invention. | Every service reinvents JWT test fixtures, problem-body assertions, and container lifecycles — inconsistently and usually wrongly. |
| **Constructor injection, no field injection** | Mandated across every platform bean; no `@Autowired` on constructors (implicit). | Immutable, testable beans with explicit dependencies; failures are compile-time or startup-time. | Beans become unit-testable only via reflection, and hidden dependencies proliferate. |
| **Documented decision log + ADRs** | Ten ADRs plus a running `decision-log.md`; deviations from a spec must be recorded as `Decision: …` in the commit body and the log. | Preserves the *why* so future maintainers do not relitigate settled trade-offs or "fix" deliberate choices. | Institutional memory is lost at the first team rotation; deliberate constraints get removed as apparent oversights. |

## 2. Capability-specific Features

### 2.1 Core (`platform-starter-core`)

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| Correlation-ID filter | `OncePerRequestFilter` at highest precedence reads `X-Correlation-Id` or generates a 32-hex id, publishes it to MDC, exposes it via `RequestContext`, echoes it on the response. Configurable header name; `generate-if-missing` toggle. | Highest precedence means it wraps security and logging, so *every* log line and error — including auth failures — carries the id. | Auth-failure and filter-level logs are uncorrelated, which is exactly the population you most need to trace. |
| `RequestContext` | Thread-scoped accessor for the correlation id and extras; `open(id, extras)` is available (as `@PlatformInternal`) for tests via try-with-resources. | Gives non-web and test code the same context handle without touching MDC directly. | Every capability re-invents context propagation, and tests cannot establish context deterministically. |
| Platform exception model | `PlatformException` + `ErrorCode` (`DC-<CAP>-<NNNN>`) as the root abstraction all capabilities throw from. | One taxonomy means one mapping layer (errors) can render every platform failure consistently. | Each capability invents its own exception type and HTTP mapping; response shapes diverge per endpoint. |
| Startup capability banner | One INFO line listing active capabilities and providers: `platform: core[ACTIVE], messaging[ACTIVE] (kafka)`. Replaceable via a `platformBannerRunner` bean. | Fastest possible smoke check that platform auto-configuration ran at all. | "Is the platform even active?" costs a debug-mode restart and a condition-report read. |

### 2.2 Errors (`platform-starter-errors`)

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| RFC-9457 problem responses | `application/problem+json` with `type` (base URI + code), `title`, `status`, `detail`, `instance`, plus `code`, `correlationId`, `timestamp` extensions. | A standards-based, machine-readable error contract clients can parse once for the whole estate. | Every service invents an error envelope; clients write per-service parsers and per-service retry logic. |
| Business exception hierarchy | `BusinessException` (422), `NotFoundException` (404), `ConflictException` (409), each carrying a stable `ErrorCode`. | Domain code throws intent, not HTTP; status mapping stays in one place. | Controllers hand-map exceptions to statuses, and the same domain failure returns different codes on different endpoints. |
| Safe catch-all mapping | Unmapped exceptions → 500 with `DC-CORE-0500` and a generic detail; the real message goes only to the correlated log. | Prevents leaking stack traces, SQL, or internal hostnames to callers while keeping full diagnostics server-side. | Internal details leak to clients — a real information-disclosure vector and a compliance finding. |
| Validation mapping with redaction | `@Valid` and `ConstraintViolationException` failures → 400 with an `errors[]` extension (`field`, `message`, `rejectedValue`); password/secret/token-shaped fields are `REDACTED`. | Field-level feedback clients can bind to forms, without echoing secrets into logs or responses. | Either clients get an opaque 400, or rejected credentials are echoed back and logged. |
| Ordering discipline | Constraint advice at `@Order(0)`, catch-all platform advice at lowest precedence; extends `ResponseEntityExceptionHandler` so framework 404/405/415 keep proper statuses. | Application advice always wins for application exceptions; the platform is the last resort, never the first. | The platform swallows exceptions the service intended to handle, and framework errors get mangled into 500s. |
| `ProblemDetailCustomizer` SPI-lite | Ordered beans mutate every outgoing problem body (e.g. add `tenant`). | Cross-cutting enrichment without replacing the advice. | Enriching error bodies requires replacing the whole handler and re-implementing its mapping logic. |
| Build-time error-code registry gate | Asserts `DC-<CAP>-<NNNN>` format and platform-wide uniqueness; exports `target/error-codes.csv` feeding the generated reference. | Codes are a support contract; duplicates make them useless for triage. | Two capabilities ship the same code, and runbooks/alerts keyed on codes silently misroute. |

### 2.3 Logging (`platform-starter-logging`)

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| JSON-by-default structured logs | Logstash-encoded, one line per event, ECS-ish fields: `@timestamp`, `level`, `logger`, `message`, `service`, `correlationId`, `stack_trace`. | Log aggregation needs structure; parsing free-text at ingest is fragile and expensive. | Grok patterns per service, brittle ingest pipelines, and fields that cannot be queried or alerted on. |
| Pre-context configuration via `EnvironmentPostProcessor` | The platform's single `spring.factories` registration defaults `logging.config` to the shipped `logback-platform.xml` through a lowest-precedence source. | Logging must be configured *before* the application context exists, otherwise early startup lines are unstructured. | Startup and failure-analysis logs — the ones that matter during an incident — are the ones that miss structure. |
| Human console mode | `local` profile falls back to Boot's readable console format; explicit `dc.platform.logging.format` always wins. | Machine format in deployed environments, human format on laptops, with no per-developer config. | Developers either read JSON by eye or hand-maintain a local logback override that drifts from production. |
| MDC lift-through | All MDC entries (correlation id included) become JSON fields; toggleable. | Free correlation between log lines and problem responses, with no per-call-site plumbing. | Correlation must be passed as an explicit argument at every log statement, and is inevitably forgotten. |
| `Kv.of(key, value)` | Structured-argument helper that stays readable in console format. | Encourages structured over string-concatenated logging without hurting local readability. | Developers concatenate values into messages, producing fields that cannot be indexed or aggregated. |
| `LogSanitizer` SPI-lite | Contributed beans scrub sensitive values from log output. | Centralised redaction policy instead of per-call-site discipline. | PII/secrets land in the log store, creating a retention and compliance problem that is expensive to remediate. |
| Fail-soft design | No error codes; a broken logging setup must never take the service down. | Observability is not worth an outage. | A malformed appender config becomes a fleet-wide startup failure. |

### 2.4 Validation (`platform-starter-validation`)

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| Platform constraints | `@NotBlankTrimmed`, `@Ulid` (26-char Crockford base32), `@SafeText` (rejects ISO control chars), `@FutureInstant` (clock-provider-based). | The constraints every DC service needs, defined once with tested semantics. | Each service writes its own ULID regex and "not blank" check, with subtly different edge-case behaviour. |
| `@SafeText` injection defence | Rejects control characters (tab/newline included) in single-line fields. | Cheap first line of defence against log injection and terminal-escape smuggling. | Attacker-controlled newlines forge log entries; escape sequences corrupt operator terminals. |
| Clock-provider-based temporal validation | `@FutureInstant` measures against the validator's `ClockProvider`. | Tests inject a fixed clock instead of sleeping — deterministic and fast. | Time-dependent tests sleep, flake, and slow the build. |
| Platform message bundle | Interpolation consults `platform-validation-messages.properties` first; applications override per key. Defaults also ship in the api jar for plain hibernate-validator use. | Consistent, overridable messages without forcing a full bundle copy. | Users see raw `{dc.platform.validation.…}` keys, or every service copies the whole bundle. |
| Method validation enabled | `@Validated` services throw `ConstraintViolationException`, mapped by errors to a 400 with `errors[]`. | Extends validation past the controller boundary into the service layer. | Service-layer preconditions are hand-coded `if`/`throw`, inconsistently mapped to HTTP. |

### 2.5 Observability (`platform-starter-observability`)

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| Common meter tags | Every meter carries `service`, `env` (first active profile), `platform.version` (from the jar manifest). | Fleet dashboards slice uniformly without per-service dashboard forks. | Each service tags differently; cross-service dashboards and alerts are impossible to build generically. |
| Health groups everywhere | `/actuator/health/liveness` and `/readiness` exist on any platform (not only Kubernetes); readiness includes `db`, `rabbit`, `redis` **when present** (`validate-group-membership=false`). | Correct probe semantics regardless of orchestrator; optional members avoid failing services that lack a dependency. | Kubernetes restarts pods that are merely warming up, or routes traffic to instances whose DB is down. |
| `/actuator/platform` endpoint | JSON `CapabilityDescriptor` report: active capabilities and providers in the running instance. | Runtime truth about platform composition — the deployment-time answer to "what's actually on?" | Composition must be inferred from build artifacts, which may not match what is deployed. |
| Prometheus local, OTLP opt-in | Both registries ship; OTLP export is **off** by default so laptops never dial a collector. | Zero-friction local metrics; explicit opt-in for collector-bound environments. | Local runs log connection errors to a non-existent collector, or local metrics require infrastructure. |
| Correlation via baggage, never as a metric tag | Correlation propagates through tracing baggage (`X-Correlation-Id`); explicitly excluded from metric tags and observation key-values. | Correlation is per-request high-cardinality; as a tag it would create unbounded time series. | Cardinality explosion — a metrics-backend outage and a large, sudden cost event. |
| `platform.capability.active{capability}` gauge | 0/1 gauge emitted per capability descriptor, feeding the org adoption dashboard. | Makes platform adoption measurable per service and per capability, not self-reported. | Adoption is tracked in spreadsheets; nobody knows which trains and capabilities are actually in production. |
| Management defaults at lowest precedence | Endpoint exposure, probes, health groups, baggage fields contributed via `platform-observability-defaults`; every key user-overridable and visible in `/actuator/env`. | Working observability out of the box without hijacking `management.*`. | Every service copies the same 8 management keys, and half get them subtly wrong. |

### 2.6 OpenAPI (`platform-starter-openapi`)

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| Zero-annotation baseline document | springdoc `/v3/api-docs` + `/swagger-ui.html` with no controller annotations required. | API documentation as a default, not a project. | Undocumented APIs; consumers integrate from Slack messages and reverse-engineering. |
| Identity defaults | Title/version default to `spring.application.name` / `info.app.version` → `dev`. | Correct identity without boilerplate in every service. | Fleet-wide "API Documentation v1.0" titles that identify nothing. |
| Platform error shape on every operation | `ProblemDetail` schema plus default 400/401/403/404/409/422/500 responses appended automatically; an operation-declared status is never overwritten. | The error contract is uniform, so documenting it per operation is pure duplication. | Clients generated from the spec have no error model and treat all non-2xx as opaque. |
| Bearer-JWT scheme documented by default | Matches the security capability's model; switchable to `NONE` for public APIs. | Generated clients get auth wiring right on first attempt. | Consumers guess the auth mechanism and generated SDKs omit credentials entirely. |
| Fail-soft generation | No error codes; documents are generated at request time, so a bad customizer affects only the document. | Documentation must never be able to break request handling. | A documentation bug becomes a production API outage. |

### 2.7 Security (`platform-starter-security`)

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| Secure-by-default filter chain | Stateless (no session), security headers on, method security enabled, `anyRequest().authenticated()` with an explicit `permit-paths` list (actuator health/info, api-docs, swagger). | Deny-by-default: a newly added endpoint is protected on the day it is written, not on the day someone remembers. | Endpoints ship unauthenticated by omission — the single most common and most damaging security defect. |
| Standard JWT resource-server wiring | Built on `spring.security.oauth2.resourceserver.jwt.*` (issuer-uri / jwk-set-uri); no platform-specific JWT configuration. | Uses the ecosystem-standard keys, so existing knowledge and tooling apply directly. | A bespoke JWT configuration dialect that must be learned, documented, and kept in sync with Spring Security. |
| RFC-9457 401/403 bodies | A dedicated entry-point / denied-handler pair writes problem bodies, because the security chain runs before `DispatcherServlet` and `@RestControllerAdvice` cannot reach it. | Auth failures look like every other error to a client — one parser for all failure modes. | 401/403 return Spring's default HTML or empty bodies while everything else returns JSON — a persistent client-side special case. |
| `CurrentUser` / `CurrentUserAccessor` | Token-format-neutral principal (subject, tenant, roles, claims), replaceable by a user-supplied bean. | Application and other capabilities (audit, flags, data auditing, restclient) depend on an abstraction, not on JWT internals. | Every consumer parses claims directly; changing IdP or token shape becomes a fleet-wide refactor. |
| `SecurityCustomizer` extension point | Ordered beans run **before** the platform's `anyRequest().authenticated()`, so they can open paths but cannot weaken the default. | Spring Security forbids adding matchers after `anyRequest()`; this ordering is the only safe one and structurally prevents accidental blanket-permit. | Customizers either fail at startup or, worse, are wired in a way that silently permits everything. |
| Explicit-only disable | `mode=disabled` is never implied by a profile, so an accidental `local` profile activation in production cannot disable security. | Profile-triggered security disablement is a well-known production breach pattern. | A misapplied profile silently removes authentication from a production deployment. |

### 2.8 Authorization (`platform-starter-security-authz`)

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| `@RequiresPermission("orders:read")` | Method- or type-level declarative permission check, enforced by a Spring AOP advisor. | Authorization intent sits next to the code it protects and is reviewable in a diff. | Permission checks are scattered `if` statements in method bodies — easy to omit, hard to audit. |
| `PermissionEvaluatorProvider` SPI | Pluggable evaluation; default `RolesClaimPermissionProvider` reads a configurable claim (default `roles`) off `CurrentUser`, falling back to derived authorities. Multiple providers compose (any grant wins). | Lets an entitlement service replace claim-based checks without touching annotated code. | Migrating from token claims to a central entitlement service means editing every protected method. |
| Correct 401 vs 403 distinction | Unauthenticated → `InsufficientAuthenticationException` (401); authenticated-but-unpermitted → `AccessDeniedException` (403); both rendered as RFC-9457 by the security chain's handlers. | Clients must distinguish "log in" from "you may not" to behave correctly. | Clients retry authentication loops against a permanent 403, or surface "session expired" for a permissions problem. |
| Independent activation | The authz starter does not transitively pull the security starter; the advisor activates only once a `CurrentUserAccessor` bean exists. | Keeps the capabilities independently useful and prevents a partially wired, silently permissive setup. | Either an unnecessary dependency, or an advisor that activates with no identity source and grants or denies everything. |

### 2.9 REST Client (`platform-starter-restclient`)

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|
| `PlatformRestClientFactory` | `builder(clientName)` returns a pre-configured `RestClient.Builder` on the JDK `HttpClient` factory. | One injection point yields correlation, timeouts, and error mapping on every outbound call. | Each service configures `RestClient.Builder` from scratch; conventions are applied inconsistently or not at all. |
| Named per-client timeouts | Defaults `connect-timeout=2s` / `read-timeout=10s`, overridable per client name. | Unbounded outbound calls are the classic cascading-failure trigger; per-name tuning matches per-dependency SLAs. | A slow dependency exhausts the caller's threads and cascades an outage upstream. |
| Correlation propagation | Current `RequestContext` correlation id sent as `X-Correlation-Id`; toggleable. | Extends single-token traceability across service boundaries automatically. | The trace stops at each hop; distributed debugging returns to timestamp guessing. |
| `RemoteCallException` mapping | Non-2xx throws with status, 1 KB-truncated body, and the remote correlation id echoed by the callee. | Preserves diagnostic context while bounding memory and log volume; the remote id links both sides' logs. | Failures surface as raw framework exceptions with either no body or an unbounded one dumped into logs. |
| Guarded bearer-token relay | When security is present and the request is authenticated, the incoming token is relayed outbound; a restclient-only consumer never pulls in security. | Propagated identity is the common need in an internal estate, without forcing a dependency on services that don't authenticate. | Every service hand-writes token relay (and often leaks tokens to the wrong hosts), or downstream calls are anonymous. |

| Feature | Description | Rationale | Impact of Absence |
|---|---|---|---|

| `new-module` Maven goal | Generates a constitution-compliant module skeleton (category, packages, POM wiring). | Removes the boilerplate cost that otherwise drives copy-paste and violations. | New modules are cloned from whatever was nearest and inherit its mistakes. |
| `upgrade-check` Maven goal | Version diff against a target BOM plus a deprecated-property scan of the service's YAML, output as console summary and `target/platform-upgrade-report.md` linking release notes. | Upgrade risk is assessable before any code changes. | Upgrades are all-or-nothing gambles, so services stay on old trains indefinitely. |
| MCP server + Claude Skill | Six read-only tools over a build-time `platform-index.json`; a generated Skill tuned to trigger on platform vocabulary. | Grounds AI-assisted development in authoritative platform facts. | Agents confidently produce vanilla-Spring code that bypasses every platform guarantee. |
| Service archetype | Generates parent, conformance test, slice tests, profile-aware `application.yml`, `CLAUDE.md`/`AGENTS.md`/`.mcp.json`/`catalog-info.yaml`, conditional messaging/data/restclient samples (Velocity `#if` renders unused samples empty; unknown feature tokens fail generation), and real-HTTP security, structured-logging, data and REST-client tests. Validated by an `-Parchetype-it` profile that generates `basic` (defaults), `service` (`data,restclient`) and `full` (relocated) projects and runs `verify` on each. | Onboarding is one command, and the generator itself is under test. | New services are assembled by copying an existing service, inheriting its stale conventions and bugs. |
| Golden-path script | isolated-repository install → invalid-input rejection → all 8 feature combinations generated outside the checkout → `mvn verify` (expected test classes ran, none skipped) → `java -jar` → readiness/auth/capability/JSON-log probes → profile and prod fail-fast probes for `data,restclient` → teardown, failing past a 10-minute per-service SLA. Uses `maven-archetype-plugin:3.1.2`, the documented version. CI job `generator-gate`. | The end-to-end developer experience is continuously verified, including its time budget. | The onboarding path breaks silently between releases and the next new team pays for it. |
| Compile-checked documentation snippets | Tagged usage snippets in the docs are compiled against the live API at build time. | Documentation examples that no longer compile are the fastest way to lose developer trust. | Copy-pasted examples fail to compile, and teams conclude the docs — and the platform — are unmaintained. |
| Local infrastructure compose file | `docker-compose.local.yml` with per-backend profiles (`kafka`, `rabbit`, `redis`, `pg`, `s3`, `vault`) for manual exploration and `-Pdocker` runs. | Real-backend exploration is available on demand without being required by the default build. | Developers either cannot exercise real backends locally, or must run all of them all the time. |
| Secrets via Spring Cloud Vault | `System.getenv` is banned by conformance rules; configuration placeholders (`${...}`) are populated by Spring Cloud Vault. | One auditable secret-delivery path instead of per-service environment-variable conventions. | Secrets arrive through ad-hoc environment variables, leak into process listings and logs, and cannot be rotated centrally. |
